# Харнесс openJiuwen Challenge

Харнесс кодового агента на `openjiuwen==0.1.20.post1`. Решает задачи из `/data/tasks` в пределах общего
бюджета токенов и пишет ответы в `answer.txt` каждой задачи и в файл `OUT`.

## Сборка и запуск

```bash
docker build -t jiuwen-harness .
docker run --rm --read-only --tmpfs /tmp:rw,size=2g --cap-drop ALL --cpus 8 --memory 16g --pids-limit 512 \
  -e LLM_BASE_URL -e LLM_API_KEY -e OUT=/data/out/answers.json \
  -v "$TASKS:/data/tasks" -v "$PWD/out:/data/out" \
  jiuwen-harness python /app/run_agent.py --tasks-dir /data/tasks
```

Необязательные переменные: `BUDGET` — бюджет в выходных токенах (без неё и без `--budget` — 100 000, ориентир
организаторов); `HARNESS_LOG_DIR` — журнал вызовов
(по умолчанию `/tmp/harness-logs`).
Локально: `python tools/docker_run.py <tasks-dir> <out-dir>`. Ключ берётся из `.env` и передаётся в контейнер
по имени переменной.

## Как работает

1. **Этап 0, без LLM.** Читаем `task.json` и делаем короткий срез папки задачи: список файлов, вывод упавших тестов,
   начало CSV и число строк, файлы базы знаний, где встречаются имена из вопроса.
2. **Этап 1, один вызов модели** `qwen3.6-35b-a3b-noreason`. Модель пишет Python-скрипт, харнесс запускает его в папке
   задачи и сам бесплатно проверяет результат: тесты зелёные, число, непустая строка.
3. **Провал — развилка** (см. «Дерево решений»): повтор этапа 1 с текстом ошибки, этап 2 (короткий ReAct) или стоп.
4. Ответ сразу пишется в `answer.txt` и атомарно в `OUT` (JSON `task_id → answer`).

## Дерево решений

```
задача ── пропустить ───────────────────────────────────────────── 0
       └─ этап 1 (c₁) ─┬─ успех, p₁ ─────────────────────────────── reward
                       └─ провал, 1−p₁ ─┬─ стоп ───────────────────── 0
                                        ├─ повтор этапа 1 (c₁ᵣ) ── успех, p₁ᵣ ── reward
                                        └─ этап 2, ReAct (c₂) ──── успех, p₂ ─── reward
```

В каждой развилке харнесс сравнивает ветки по ожидаемой ценности EMV = `p · reward − λ · цена` и идёт по лучшей
(`harness/decision.py`, без LLM):
- **λ — цена токена в баллах**: сколько дала бы ещё не начатая задача на этот токен. Бюджета хватает на все
  оставшиеся — λ = 0, и любой провал эскалируется (штрафа за неверный ответ нет). Бюджет тесный — λ равна выгоде
  на токен первой задачи, не поместившейся в жадный рюкзак, и дорогая ветка с малым `p` проигрывает стопу.
- **`p`** зависит от вида провала (`no_code`, `script_error`, `tests_fail`, `bad_format`): бета-априор
  в `config/success_model.json`, сдвиг по факту во время прогона, калибровка `python -m tools.calibrate_success`.
- **Цена** ветки — из модели расхода; ветка допускается, только если её высокая оценка помещается в резерв бюджета.
- Задача с `soft`-сигналом детектора решается, пока `p_feasible · p · reward ≥ λ · E[цена]` (`p_feasible` по коду
  сигнала — по разметке 400 сгенерированных задач); иначе `skipped_low_value`, 0 токенов. Порядок задач —
  `reward · p / E[цена]`.
- **Этап 2** (`harness/stage2.py`): модель видит свой скрипт и ошибку, может запускать Python-скрипты в папке задачи
  и сдаёт ответ строкой `FINAL:`; проверка — та же. Стоп: 6 шагов, потолок расхода ветки, повтор той же ошибки
  (провал тестов — только после шага, изменившего файлы), повтор того же скрипта (если его вывод — одна строка,
  прошедшая проверку, это ответ).

Замер этапа 2 (gen4, 2026-11-07): на 163 `hard`-задачах этап 1 не справился с 8 (все coding), этап 2 спас 8 из 8
по ~400–770 токенов; в режиме `--force-stage2` (этап 2 с нуля) — 31 из 32, в среднем 2 шага. Калибровка: `p₂` = 0.84,
после провала тестов 0.61; цена этапа 2 — по типам (search ≈2 тыс., data_analysis ≈220).
Проигрыш журналов gen3 × 2 + примеры + `hard` gen4 при бюджете 25/50/75/90 % от полного расхода: 417/618/764/818
баллов против 415/612/766/811 у порядка только по цене и 296/557/748/808 у прежних констант; перерасходов 0 против 1.
Выигрыш мал, потому что этап 1 решает 96–99 % задач: этап 2 — страховка для скрытого набора, где провалов больше.

## Учёт и оценка расхода

- Стоимость вызова: `completion_tokens + prompt_tokens / 10`. Рассуждения уже входят в `completion_tokens`
  (проверено замером 2026-11-07). Общий счётчик `BudgetLedger` ведётся по `usage` из ответа.
- Два прохода. Сначала для всех задач без LLM: детектор невыполнимых и сборка промпта этапа 1. Затем задачи
  стартуют в порядке `reward / ожидаемая цена`; задача допускается, только если её высокая оценка помещается
  в остаток бюджета за вычетом резерва задач, которые уже решаются (перерасход обрывает весь запуск);
  не поместившиеся получают второй проход, когда резервы сменятся фактической ценой.
- Модель расхода `harness/cost_model.py`: вход — длина готового промпта / символов на токен (по типу:
  search ~2.8, math ~3.9), выход — среднее и p90 по типу, плюс ожидаемая цена повтора; во время прогона
  среднее выхода и масштаб входа сдвигаются к факту. Параметры `config/cost_model.json` пишет
  `python -m tools.calibrate_cost <tasks-dir>=<log> ... --out config/cost_model.json`.
- Проверка на журналах (gen3 × 2 + примеры, 120 задач, калибровка на одной половине — проверка на другой):
  ошибка оценки WAPE 0.23 против 1.01 у прежних констант по типу; факт выше высокой оценки у 8 % задач.
  Проигрыш журналов при урезанном бюджете (`python -m tools.simulate_budget`): при 25/50/75/90 % от полного
  расхода баллы 134/230/277/303 против 112/189/271/299 у прежнего порядка; перерасход в 1 сценарии из 24 против 18.
- Одновременно к модели идут не больше 3 запросов: таков лимит прокси на ключ.

## Невыполнимые задачи

Перед вызовом модели детектор `harness/feasibility/` проверяет задачу без LLM и без запуска её кода:
- общая проверка: файлы и папки, названные в инструкции, существуют (`sales.csv`, `kb/`);
- `coding`: тесты компилируются и не требуют от одного и того же вызова двух разных ответов;
- `data_analysis`: в CSV есть столбцы, которые обещает инструкция и которые нужны для вопроса;
- `math`: все количества заданы числами, нет деления на 0;
- `search`: человек из вопроса есть в базе знаний, цепочка «работодатель → штаб-квартира» не рвётся, нужное поле
  есть у карточки (если у других карточек оно есть).

Сигнал `hard` (доказано) — задача пропускается: ни токенов, ни ответа. Сигнал `soft` (спорно: продукта нет в CSV,
месяц 13, отсутствует `mylib.py`, который можно написать по тестам) только пишется в журнал — ответ «0» может
оказаться правильным. Ключевые слова — `config/feasibility.json`, политика — `feasibility.skip_severities`.

Проверка на своих наборах (генератор `tools/gen`, разметка `_labels.json`): на 400 задачах с 20 % невыполнимых
точность 1.0, полнота 66 % по `hard` (все `hard`-виды пойманы, `soft`-виды по политике решаются), с `soft` — 100 %;
на 8 примерах организаторов и 400 выполнимых задачах ложных пропусков нет. Цифры — на собственных шаблонах,
на скрытом наборе полнота будет ниже.

## Что видно в консоли

stdout пуст: журнал openjiuwen идёт только в его файл (`./logs/logs/run/jiuwen.log` от текущей папки). Всё наше —
в stderr, по ходу прогона:

```text
coding_0396: tests_fail → stage2 (EMV 1,5 > retry 1,0)        развилка: выбранная ветка и лучшая отвергнутая
429: пауза 61 с (задача search_0122)                          пауза прокси, без промпта
coding_0007: решена, цена 287, ответ 'DONE'                   итог задачи (с этапом 2 — шаги и причина стопа)
[ 37/163 | в работе 3 | осталось 123 ]  токены 21 480 / резерв 2 950 / 100 000  λ 0  429: 1
Итог: 8/8 задач — решена 8; токены 1 920 из 100 000; этап 2 спас 0 из 0
```

Строка прогресса в терминале обновляется на месте (не чаще раза в `refresh_sec`); если stderr перенаправлен в
файл или в `docker logs`, она печатается обычной строкой раз в `plain_every_sec`. Символы, которых нет в
кодировке потока (`→`, `λ` в cp1251), заменяются (`->`, `lambda`). Форматы и интервалы — `config/console.json`.
Консоль только читает журнал: при сбое записи она выключается, а решение задач и расход не меняются.

## Траектории

Каждый вызов и итог задачи пишутся в JSONL (`HARNESS_LOG_DIR`): модель, токены, стоимость, этап, результат.
На 8 примерах организаторов: 8/8 решено, около 2 тыс. выходных токенов на весь набор.

Тренировочные наборы генерирует `python -m tools.gen --out <dir> --n 60 --seed 1 --infeasible 0.2`: четыре типа
задач в формате примеров, обычные и усложнённые (10–14 функций, 1–5 тыс. строк CSV, 6–10 шагов, поиск в 3 хопа)
и невыполнимые 16 видов. Оценка детектора без LLM — `python -m tools.gen.eval_detector <dir>`, отчёт прогона —
`python -m tools.gen.report <dir> logs/run-*.jsonl`. Прогон на 60 задачах (12 невыполнимых): 151 из 151 возможного
балла, 48/48 выполнимых, 19.4 тыс. выходных токенов (из них 0.5 тыс. — на спорные невыполнимые, которые по политике решаются).
