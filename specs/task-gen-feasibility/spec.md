# Генераторы задач и детектор невыполнимых на этапе 0

## Зачем
В финальном наборе 15–25 % невыполнимых задач: каждая, отданная модели, тратит токены впустую (при равных баллах
выигрывает тот, кто потратил меньше). Нужны: (1) свой тренировочный набор задач в формате примеров — обычные,
усложнённые и невыполнимые, с разметкой; (2) бесплатный детектор невыполнимых до вызова модели, который не
выбрасывает выполнимые задачи; (3) числа: баллы, токены, точность и полнота детектора на прогоне.

## Критерии готовности (проверяемые)
- [ ] `python -m tools.gen --out D:\claude-tmp\jiuwen-runs\gen<N> --n 60 --seed 1 --infeasible 0.2` создаёт 60 папок
      `<type>_<NNNN>/task.json` (+ `workspace/`) в формате примеров (поля `task_id, task_type, instruction, reward,
      expected, check`, тексты инструкций — как у организаторов) и `_labels.json` в корне набора
      (`task_id → feasible, variant, kind, severity, expected`). Тот же `--seed` → побайтно тот же набор.
- [ ] Типы 4 × варианты: `base` (как примеры), `hard` (больше функций и багов; 1–5 тыс. строк CSV и фильтр по региону
      или выручка; 6–10 шагов в math; 3 хопа и большая kb с похожими именами в search) и `infeasible` (виды ниже).
- [ ] Для каждой выполнимой сгенерированной задачи `expected` верен: тест прогоняет эталонное решение
      (coding: исходный `mylib.py` → тесты зелёные, сломанный → красные; data/math/search: независимый пересчёт).
- [ ] Детектор `harness/feasibility/` на этапе 0 (без LLM, без запуска кода задачи) выдаёт сигналы
      `код, тяжесть (hard|soft), пояснение`; харнесс пропускает задачу (нет `answer.txt`, 0 токенов, статус
      `skipped_infeasible` в журнале) только по `hard`; какие тяжести пропускать — в конфиге.
- [ ] 0 ложных срабатываний `hard` на 8 примерах организаторов и на 400 сгенерированных выполнимых задачах (тест).
- [ ] Полнота `hard` по `hard`-видам невыполнимых генератора ≥ 90 % (офлайн, без LLM, `tools/gen/eval_detector.py`).
- [ ] Прогон харнесса на gen-наборе 40–60 задач и на 8 примерах: в отчёте баллы / максимум, выходные токены
      (всего и потраченные на нераспознанные невыполнимые), точность и полнота детектора; журналы `logs/run-*.jsonl`.
- Ключевой критерий парой (тесты в `tests/test_feasibility.py`):
  - должно пройти (не помечено): `search_0005` («Sergei Garcia's employer» → Fjord Data → Osaka); data-задача, где
    продукт есть, но в выбранные месяцы продаж нет (ответ 0 — законный); coding, где одна функция проверяется
    двумя разными вызовами с разными ответами;
  - должно быть отклонено (`hard`): та же search-задача, но имени «Sergei Garcia» нет ни в одном файле kb; coding,
    где один и тот же вызов `m.total([1, 2, 3])` проверяется на 6 и на 7.

### Виды невыполнимых (генератор → ожидаемая тяжесть в детекторе)
| Тип | Вид | Тяжесть |
|---|---|---|
| все | файла/папки из инструкции нет (`sales.csv`, `kb/`) | hard |
| coding | нет `mylib.py` или `test_mylib.py` (код агент может написать сам — спорно) | soft |
| coding | противоречивые тесты (один вызов — разные ожидаемые значения) | hard |
| coding | синтаксическая ошибка в тестах (тесты править нельзя) | hard |

Уточнение при реализации (2026-11-07): вид «тесты импортируют несуществующий модуль» убран — агент может создать
модуль в папке, задача выполнима; отсутствующий `.py` понижен до soft по той же причине.
| data_analysis | в CSV нет столбца, нужного для вопроса (`units`, `price`, `region`) | hard |
| data_analysis | продукта/региона из вопроса нет в CSV | soft |
| data_analysis | месяцы вне 1..12 («months 13 through 14») | soft |
| math | нет начального числа («an unknown number of boxes») или число заменено словом («some», «several») | hard |
| math | деление на 0 («split equally into 0 warehouses») | hard |
| math | вопрос о величине, которой нет в условии («How many crates…» при boxes) | soft |
| search | сущности из вопроса нет в kb | hard |
| search | у найденной сущности нет нужного поля, а у других сущностей этого вида оно есть | hard |
| search | цепочка рвётся: работодатель/наставник указан, но его файла нет | hard |

`soft` — спорные случаи (ответ «0» может оказаться правильным): по умолчанию задача решается, сигнал пишется в журнал;
`eval_detector.py` считает оба варианта политики (пропуск только `hard` и `hard+soft`).

## Не входит (non-goals)
- Модель расхода и `p_feasible` для планировщика (следующий шаг плана), этап 2 (ReAct).
- Ответ без LLM для «тесты уже зелёные» и другие короткие пути решения.
- Распознавание невыполнимости после этапа 1 (скрипт упал, ответ пуст) — отдельная задача.
- Особый ответ для невыполнимых («INFEASIBLE»): пока пропускаем; формат уточнить у организаторов.
- Прогон на моделях с рассуждением и сотни задач — только 40–60 + 8 примеров.

## Ограничения
- Безопасность/данные: `.env` не читаем; сгенерированные наборы и копии для прогонов — только в
  `D:\claude-tmp\jiuwen-runs\gen<N>` / `run<N>` (не в репо). Детектор не исполняет код задачи (только `ast.parse`,
  чтение файлов, `importlib.util.find_spec`), поле `expected` не читает (в финале оно, вероятно, скрыто).
- Архитектура: новый пакет `harness/feasibility/` — по одному модулю на тип + общий (файлы из инструкции) +
  агрегатор; `run_agent.py` вызывает его перед решателем. Генератор — `tools/gen/` (по модулю на тип + CLI).
  «Менеджеров» не добавляем.
- Контент: словари генератора (имена, фамилии, компании, города, продукты, регионы, пул функций с багами и
  тест-кейсами) — файлами в `tools/gen/content/`; ключевые слова детектора (синонимы полей, слова-заменители чисел,
  стоп-слова) — `config/feasibility.json`.
- Внешние контракты: формат `task.json`, `OUT`, `answer.txt` не меняется. В журнал добавляется статус
  `skipped_infeasible` с сигналами — совместимо (читают только наши `tools/`). Новая секция конфига `feasibility`.

## Пре-мортем
- Допущение о коде (проверено Read): `load_tasks` берёт только `*/task.json` → `_labels.json` в корне набора харнесс
  не видит; `Task.workspace` при отсутствии `workspace/` возвращает папку задачи → детектор ищет файлы в обеих;
  `WorkspaceSnapshot` запускает тесты подпроцессом — детектор стоит раньше, пропущенные задачи тестов не запускают;
  `ResultsWriter.record` вызывается только при ответе → пропуск не пишет `answer.txt`.
- Главный риск — ложные срабатывания на скрытых шаблонах (другие формулировки, другие поля kb). Защита: `hard` только
  при положительно найденном доказательстве (файл назван и отсутствует; сущность найдена, а поле есть у соседей и нет
  у неё); если разбор не удался — «не знаю» = выполнима. Нераспознанная невыполнимая стоит ~300 токенов, ложный
  пропуск — весь reward задачи.
- Частичный сбой: битый `task.json`/CSV/нечитаемый файл → детектор ловит исключение и считает задачу выполнимой
  (сигнал `detector_error` в журнал), прогон не падает. Сеть детектору не нужна.
- Одновременность: детектор только читает файлы; задачи изолированы по папкам; генератор пишет в новую папку и
  отказывается писать в непустую.
- Источник ожидаемых значений в тестах: разметка генератора (`_labels.json`, пересчитанная независимым кодом),
  `expected` примеров организаторов, таблица видов из этого spec.
- Не заметит verify.sh: качество на скрытом наборе (только прогон и ответы организаторов), токены и баллы прогона
  на API — смотреть отчёт вручную.
