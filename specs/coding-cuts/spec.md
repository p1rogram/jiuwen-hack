# Сокращение токенов на coding-задачах

## Зачем
После token-cuts `coding` — около 2/3 расхода: run31 (`logs/run-20261109-205030.jsonl`, 127 задач) — 21 401 из 32 039,
из них выход 16 820 (79 %). Медиана выхода этапа 1 — 385, p90 — 892; выход ≈ 1,2–4 × размер всего `mylib.py`
в токенах: модель переписывает файл целиком и рассуждает комментариями. При равных баллах места решает расход.

Проба 2026-11-09 (3 hard-задачи gen4: 0167, 0057, 0290; копии `D:/claude-tmp/jiuwen-runs/probe-coding1|2`, все 9 решены):
A — текущий промпт 2 851; B — хвост «правки через `s.replace`» 2 451 (−14 %); C — то же + «кратчайший уникальный
фрагмент, один короткий комментарий» 2 258 (−21 %). Модель всё равно повторяет функцию целиком в old и new;
комментарии — 25–60 % ответа. На 0290 (небольшой файл) C дороже A (440 против 419 выхода).

## Критерии готовности (проверяемые)
### Шаг 1. Хвост формы ответа для coding
- [ ] `stage1.tail_prompts` получает `coding` → `prompts/stage1_tail_coding.txt`: чинить точечно (`s.replace(old, new, 1)`,
      old — кратчайший уникальный фрагмент), файл целиком не переписывать, не больше одного короткого комментария на баг,
      тесты не запускать и ничего не печатать; **если нужного файла нет — написать его целиком** (soft `missing_file`).
      Текст не называет `mylib.py`: в скрытом наборе файлы могут называться иначе.
- [ ] Замер на всех coding набора run31 (35 задач gen4, исходные копии из `gen4`) + coding gen3 (15, из них 13
      выполнимых) + 2 примера; база — run31 / run29 / run30 по тем же задачам.
- [ ] Шаг принимается, только если: решённых coding не меньше, чем в базе; суммарная цена coding ниже хотя бы на 10 %;
      у задач с маленьким файлом (`mylib.py` < 600 байт) цена в сумме не выросла больше чем на 5 %.
      Иначе — хвост только для задач с большим срезом (порог по `prompt_chars`) или откат.
- Ключевой критерий парой (тест `tests/test_prompt_tail.py`):
  - должно пройти: сообщение `coding` заканчивается текстом `stage1_tail_coding.txt`;
  - должно быть отклонено: тип без записи в `tail_prompts` (например, неизвестный `other`) получает сообщение без хвоста —
    как до изменения. Тест `test_coding_has_no_tail` (ожидание из token-cuts шаг 3) заменяется — новое ожидание из этой spec.

### Шаг 2 (условный). Формат правок, который применяет харнесс
Только если шаг 1 дал меньше 20 % на coding. Модель отвечает блоками правок без обвязки `open/read/write`
(формат — решить в открытых вопросах), харнесс применяет их в папке задачи и запускает тесты; не применилась правка →
провал `script_error` с понятным текстом для повтора. Критерии и тесты — дописать после шага 1.

### Шаг 3. Перекалибровка
- [ ] `python -m tools.calibrate_cost ... --keep-stage2 --eval` по журналам замера: WAPE coding и доля «факт > high»
      не хуже текущих; запись `config/cost_model.json`; README и `docs/DECISIONS.md`.

## Не входит (non-goals)
- Смена модели этапа 1 и этапа 2, правка промптов этапа 2.
- Решатели без LLM, разбор багов по шаблонам нашего генератора (переобучение на свои шаблоны).
- Запрет комментариев целиком: это рассуждение модели, без него падает точность (token-cuts шаг 3).

## Ограничения
- Безопасность/данные: ключ — только `.env`, не читать; прокси — не больше 3 запросов одновременно.
- Архитектура: меняются `config/harness.json` (`stage1.tail_prompts`), новый `prompts/stage1_tail_coding.txt`,
  тест хвоста; `Stage1Prompt` уже умеет хвост по типу — кода в `harness/` на шаге 1 нет.
- Контент: текст хвоста — в `prompts/`, порог (если понадобится) — в `config/harness.json`.
- Внешние контракты: формат `answer.txt` / `OUT` не меняется; журнал — те же поля.

## Пре-мортем
- Допущение о коде (проверено Read 2026-11-09): у `coding` хвоста нет (`config/harness.json`, `tail_prompts` —
  search/math/data); для `unittest` ответ — `DONE` из `Verifier._check_tests`, stdout скрипта не нужен
  (`harness/verifier.py:86`) — печатать DONE модели не обязательно.
- Главный риск: в token-cuts шаг 3 «замена через `str.replace` удлиняла выход» (проба тогда — на малых файлах).
  Отсюда условие по маленьким файлам в критериях шага 1.
- Частичный сбой: `assert old in s` падает (old скопирован неточно) → `script_error` → повтор с хвостом stderr; повтор
  обычно переписывает файл целиком — цена выше базы. Считать долю таких повторов в замере.
- soft `missing_file` (нет `mylib.py`): хвост не должен мешать написать файл с нуля — проверить на 10 таких задачах набора run31.
- Одновременность: не касается (промпт); прогоны — в новых папках `run<N>`.
- Источник ожидаемых значений: эта spec (критерии шага 1), база — журналы run29–31.
- Не заметит verify.sh: точность и цену — только живой замер на модели; разброс при temperature 0 есть
  (одна задача 419 → 440) — сравнивать суммы, не отдельные задачи.
