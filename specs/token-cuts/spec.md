# Сокращение токенов на решённую задачу

## Зачем
По письменному обзору организаторов и чату участников выполнимые задачи решают почти все, поэтому места, скорее
всего, решит правило «при равенстве баллов — меньше токенов». Замер `logs/run-20261107-164542.jsonl` (163 задачи,
цена на задачу в экв. токенах): search 832, из них вход ≈ 80 % (срез `kb/` ~18 000 символов: список ~100 файлов и
тела всех файлов до лимита `snapshot.max_total_chars`); coding 967; math 243; data_analysis 134. Источник идей —
разведка «Аргон» 2026-11-09 (вердикт — база, `Strategy.md`).

## Критерии готовности (проверяемые)
### Шаг 1. Узкий срез базы знаний (search)
- [x] Если в рабочей папке больше `snapshot.kb_min_files` текстовых файлов и среди них есть файлы, чей заголовок
      `# <Имя>` совпадает с именем из инструкции (семена), в промпт идут только семена и файлы, достижимые от них по
      значениям строк `Ключ: Значение` (значение = заголовок другого файла), не глубже `snapshot.kb_follow_depth`
      шагов и не больше `snapshot.kb_max_files` файлов.
- [x] Остальные файлы в списке FILES не перечисляются поимённо: одна строка «ещё N файлов в kb/ не показаны».
- [x] Семян нет (неизвестная сущность и т. п.) — срез как раньше (ранжирование по совпадениям до лимита символов).
- [x] Папки с ≤ `kb_min_files` текстовыми файлами (coding, data, math) — срез без изменений.
- [x] Офлайн-проверка без LLM (`tools/eval_slice.py`): на выполнимых search из gen3, gen4, gtest2 и примерах
      `expected` встречается в срезе у 100 % задач; медиана длины среза search уменьшается не меньше чем в 2 раза.
- Ключевой критерий парой (тесты `tests/test_snapshot_kb.py`):
  - должно пройти: вопрос «город штаб-квартиры работодателя наставника X» — в срезе файлы X, наставника, компании
    наставника; файла посторонней компании нет;
  - должно быть отклонено (то есть не сузить): имя из вопроса не совпадает ни с одним заголовком — срез включает
    файлы по старому ранжированию (как до изменения).

Итог шага 1 (2026-11-09): `tools/eval_slice.py` — expected в срезе у 172/172 выполнимых search (примеры 2, gen3 11,
gen4 83, gtest2 76); медиана среза 4921→914, 6562→953, 10207→974, 6473→974 символов. Живой прогон примеров
(run24): 8/8, 1703 токена (run22 было 1826); search вход 2046–2114 → 534–574 токена; выход search_0005 колеблется
248–421 (модель пишет разбор файлов даже при ответе в промпте) — к шагу 3.

### Шаг 2. Выход UNSOLVABLE на этапе 1 — после замера шага 1
- [x] Системный промпт разрешает скрипту напечатать маркер отказа, если данных для точного ответа нет
      (`prompts/system_unsolvable.txt`, добавляется при `stage1.unsolvable_enabled`).
- [x] Маркер → задача завершается статусом `unsolvable`, без повтора и этапа 2, без `answer.txt` (`tests/test_unsolvable.py`).
- [x] Замер на выполнимых задачах gen4: доля ложных отказов ≤ 1 %; иначе шаг не включается (флаг в конфиге).

Итог шага 2 (2026-11-09, run27, `logs/run-20261109-201232.jsonl`): 100 выполнимых gen4 (по 25 каждого типа) +
27 невыполнимых `soft` — ложных отказов 0/100, но и верных отказов 0/27: модель считает «месяц 15», «ящики → коробки»,
пишет недостающую библиотеку. Экономии нет, а правило — ~70 входных токенов на каждый вызов этапа 1, поэтому
`unsolvable_enabled: false`. Код оставлен: включается флагом, если найдётся формулировка с верными отказами.
Прогон: 127/127 решены по локальной проверке, 46 567 токенов; невыполнимые soft стоили 13 395 (coding 905 на задачу,
math 553, data 132) — экономить можно только там, где после этапа 1 идут повтор и этап 2.

### Шаг 3. Короче выход модели — после шага 2
- [x] Промпт требует код без комментариев и пустых строк; замер `out` на gen3 до/после, точность не ниже.

Итог шага 3 (2026-11-09): правило в системном промпте модель не выполняла (проба на 3 задачах — комментарии и
отладочный вывод остались), в конце сообщения задачи — выполняет. Хвост по типу — `stage1.tail_prompts`

правило их не убирает, а замена через `str.replace` удлиняла выход. Тест `tests/test_prompt_tail.py`.
gen3, 60 задач, run28 → run29 (`logs/run-20261109-202252.jsonl` → `run-20261109-202828.jsonl`): точность 48/48 → 48/48,
ответы совпали; токены 15 920 → 12 119 (−24 %); search 3581 → 796 (выход 2970 → 135), math 2191 → 1264,
data 1799 → 1788, coding 8349 → 8271. Примеры (run30): 8/8, 1117 токенов (run24 было 1703).

## Не входит (non-goals)
- Детерминированные решатели без LLM — отдельная спека, если останется время.
- Смена моделей этапов и калибровка EMV.
- BM25 и внешние библиотеки поиска: связи в `kb/` явные (`Ключ: Значение`), хватает обхода по заголовкам.

## План
1. `harness/snapshot.py`: обход связей kb, конфиг `snapshot.kb_*` в `config/harness.json`; тесты; `tools/eval_slice.py`.
2. Шаг 2 (промпт, solver/verifier, статус) — после замера шага 1.
3. Шаг 3 — промпт, замер.
