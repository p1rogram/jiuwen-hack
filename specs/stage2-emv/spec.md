# Этап 2 (короткий ReAct) и выбор ветки по ожидаемой ценности (EMV)

## Зачем
Сейчас у задачи одна дорога: этап 1 (вызов → скрипт → проверка, 1 повтор), не вышло — задача потеряна. Выбор задач
учитывает только цену (`reward / E[цена]`), а вероятность успеха считается равной 1. Идея менеджера (дерево решений
из геологии, «бурить или не бурить»): в каждой развилке сравнивать ветки по EMV = `Σ p·исход − цена` и идти по
лучшей. У нас три развилки, где это меняет решение:

```
задача ── пропустить ───────────────────────────────────────────── 0
       └─ этап 1 (c₁) ─┬─ успех, p₁ ─────────────────────────────── reward
                       └─ провал, 1−p₁ ─┬─ стоп ───────────────────── 0
                                        ├─ повтор этапа 1 (c₁ᵣ) ── успех, p₁ᵣ ── reward
                                        └─ этап 2, ReAct (c₂) ──── успех, p₂ ─── reward
```

1. **Решать или пропустить** задачу с `soft`-сигналом детектора: `p_feasible(сигнал) · p₁ · reward` против цены.
2. **После провала этапа 1** — стоп, повтор или ReAct: у каждой ветки своя `p` (зависит от вида провала) и цена.
3. **Порядок задач**: `reward · p_success / E[цена]`, где `E[цена]` включает ожидаемую цену ветки после провала.

Цена переводится в баллы через **λ — цену токена**: сколько баллов дал бы этот токен в лучшей из ещё не начатых
задач. Если бюджета хватает на всё (`Σ E[цена] оставшихся ≤ доступно`) — λ = 0: решаем всё выполнимое и
эскалируем любой провал (штрафа за неверный ответ нет). Если бюджет тесный — λ = отношение `p·reward / E[цена]`
первой задачи, не помещающейся в жадный рюкзак; ветка выбирается, только если `p · reward > λ · цена`.
Это и есть «умножаем риск на цену» — но с ценой, привязанной к остатку бюджета, а не постоянной.

## Критерии готовности (проверяемые)
- [ ] `harness/success_model.py` (`SuccessModel`): `p` по ключу `(ветка, тип[, вид провала])` — бета-априор из
      `config/success_model.json` (`alpha`, `beta`), сдвиг по факту во время прогона; `p_feasible` по коду
      `soft`-сигнала детектора. Неизвестный ключ → априор ветки `default`.
- [ ] Вид провала этапа 1 — из `Verdict`: `no_code`, `script_error` (исключение/таймаут), `tests_fail`,
      `bad_format` (нет числа / пустой вывод) — пишется в журнал.
- [ ] `harness/decision.py` (`DecisionPolicy`, без LLM и ввода-вывода): `lambda_(оставшиеся, доступно)`,
      `branch(задача, вид провала, λ, допустимые ветки) → stop | retry | stage2` по максимуму
      `p_feasible·p·reward − λ·цена` (с допуском по `high` ветки через `BudgetLedger.reserve`; повторный резерв
      задачи заменяет её прежний), `skip_soft(задача, λ) → bool` (сигналы — из `Prepared.signals`), `priority(задача)`.
      Развилки обходит `harness/pipeline.py` (`TaskPipeline`): этап 1 → ветка → после неудачного повтора ещё одна
      развилка (`stage2` или `stop`); после этапа 2 веток нет. `Outcome` вынесен в `harness/outcome.py`.
- [ ] `harness/stage2.py` (`Stage2Solver`) — свой короткий цикл через `LlmGateway` (учёт, семафор 3, журнал — как
      у этапа 1), не `ReActAgent`: контекст стартует с сообщений этапа 1 + последний скрипт + ошибка; один
      инструмент `run` — блок ```python, который запускается в папке задачи (как скрипт этапа 1: без shell, одинаково
      в Windows и в контейнере; таймаут, хвост вывода), ответ — строка `FINAL: <ответ>`; проверка — тот же
      `Verifier`; у `unittest` зелёные тесты после скрипта завершают цикл без `FINAL`. Стоп: лимит шагов
      (`config/harness.json` → `stage2.max_steps`), бюджет задачи = `high` ветки (потрачено + оценка шага > бюджета →
      стоп), повтор того же скрипта или той же ошибки дважды (ошибка этапа 1 — первое появление; «та же» — та же
      последняя строка исключения). Причина стопа — `stage2_stop` в журнале.
- [ ] `CostModel` получает параметры ветки `stage2` (цена шага и число шагов по типу); пока данных нет —
      значения из конфига с пометкой `prior`, калибровка `tools/calibrate_cost` подхватывает журналы этапа 2.
- [ ] Повтор этапа 1 перестаёт быть безусловным: идёт через `DecisionPolicy.branch` (ветка `retry`).
- [ ] Журнал задачи: `p_success`, `p_feasible`, `lambda`, по каждой развилке — ветки с `p`, ценой и EMV, выбранная
      ветка; вызовы этапа 2 — `stage: stage2.<шаг>`. `tools/gen/report.py` показывает спасённые этапом 2 задачи
      и токены этапа 2.
- [ ] `python -m tools.calibrate_success <tasks-dir>=<log> ... --labeled <set-dir> ...` пишет
      `config/success_model.json`: `p` веток по журналам; `p_feasible` по кодам `soft` — по `_labels.json`
      сгенерированных наборов (gen4: 400 задач с разметкой, без LLM). Ручные априоры — раздел `priors` того же файла:
      каждый запуск = `priors` + все переданные данные (без накопления). `p_feasible.default` (коды, которых в
      наборах нет) не калибруется — остаётся априором.
- [ ] `tools/simulate_budget.py` учитывает `p_success` в порядке и ветку после провала (провалы и цена этапа 2 —
      из журналов, где они есть).
- [ ] Регрессия: примеры 8/8, расход не выше прежнего (этап 2 на них не нужен); тесты зелёные.
- Ключевой критерий парой (тесты `tests/test_decision.py`, `tests/test_stage2.py` с поддельным шлюзом):
  - должно пройти: бюджета хватает на всё (λ = 0), этап 1 провалился с `tests_fail`, `p₂ = 0.3` → ветка `stage2`;
    задача с `soft`-сигналом при λ = 0 решается;
  - должно быть отклонено: бюджет тесный, `p₂ · reward < λ · c₂` → `stop`, ни одного вызова `stage2`, статус
    `unverified`; задача с `soft`-сигналом, `p_feasible = 0.1`, при тесном бюджете → `skipped_low_value`, 0 токенов;
    цикл этапа 2, дважды получивший ту же ошибку, останавливается до лимита шагов.

## Откуда берутся вероятности
- `p_feasible` по `soft`-кодам — уже есть даром: разметка gen4 (детектор офлайн, `tools/gen/eval_detector`).
- `p₁` по типу — журналы этапа 1 (на gen3 почти 1.0: 151/151 — на скрытом наборе ниже `#гипотеза`).
- `p₁ᵣ`, `p₂` и цена этапа 2 — данных нет: провалов этапа 1 у нас единицы. Источники: (а) прогон `hard`-задач gen4;
  (б) режим `--force-stage2` — этап 2 на задачах, где этап 1 искусственно «провален» (без вызова этапа 1), чтобы
  померить `p₂` и цену шага. Оба — расход токенов, **только с согласия владельца**; до них — априор из конфига,
  осторожный (`p₂` ≈ 0.3, цена ≈ 4 шага).

## Вне рамок
- Выбор модели (с рассуждением как третья ветка) — та же схема, отдельным шагом после данных этапа 2.
- GBDT для `p` и цены — после сотен провалов в журналах.
- «Инструменты харнесса» (LLM только извлекает параметры) — ждёт ответа организаторов.

## Риски
- Вероятности на десятке провалов шумные → бета-априор и поправка по ходу; решения при λ = 0 от `p` не зависят.
- ReAct перечитывает контекст на каждом шаге: 4 шага по ~2k входа = ~800 токенов только на вход → жёсткий лимит шагов
  и бюджет задачи = `high` ветки.
- Время: этап 2 в 3–6 раз дольше этапа 1; при 100 задачах за 1 ч — эскалировать в первую очередь задачи с лучшим EMV,
  что политика и делает.
- `Harness` растёт: развилки — в `DecisionPolicy`, сам `Harness` только вызывает её (лимит размера классов).
