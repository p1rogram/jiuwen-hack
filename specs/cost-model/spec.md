# Модель расхода и выбор задач под бюджет

## Зачем
Сейчас порядок задач — `reward / cost_estimate_by_type` (константы 1200/400/300/300), допуск задачи —
`remaining >= estimate` без учёта задач, которые уже решаются параллельно. Константы мимо факта в 2–3 раза:
по журналам gen3 (`logs/run-20261107-115711.jsonl`, `run-20261107-120828.jsonl`, 52 решённых задачи × 2) средний
расход — coding 560 (оценка 1200), data_analysis 126 (400), math 170 (300), search 670 (300). Разброс внутри типа
большой: coding 115–1119, search 345–1158. При тесном бюджете жадный выбор по неверной цене берёт не те задачи,
а перерасход опасен: когда бюджет кончается, прокси перестаёт отвечать и запуск завершается принудительно.

Что известно из журналов:
- входные токены — заметная часть цены (search: вход ~4400 × 0.1 = 440 из ~670), и промпт полностью известен
  **до** вызова модели (срез папки `WorkspaceSnapshot` строится без LLM) → вход можно считать почти точно;
- выход зависит от типа: data ~90, math ~140, search ~210, coding ~430 (p90 — 890);
- повтор этапа 1 редок (1 из 112 задач), но стоит второго вызова с удлинённым контекстом.

## Критерии готовности (проверяемые)
- [x] `harness/cost_model.py` (`CostModel`): оценка задачи по уже собранному промпту —
      `mean` и `high` в выходных токенах:
      `вход = input_weight × (prompt_chars / chars_per_token + overhead_tokens)`,
      `выход = out_mean[type]` (для `high` — `out_p90[type]`),
      `+ p_retry[type] × (цена второго вызова: вход первого + его выход + шаблон повтора, и выход ещё раз)`.
      Неизвестный тип → параметры `default`.
- [x] Параметры — в `config/cost_model.json` (не литералы в коде); их пишет калибровка
      `python -m tools.calibrate_cost <tasks-dir>=<log> [...] --out config/cost_model.json`: по парам «набор + журнал»
      заново строит промпт каждой задачи, подбирает `chars_per_token`/`overhead_tokens` (МНК по `input_tokens`
      первого вызова) и по типам `out_mean`, `out_p90`, `p_retry`, `n`.
- [x] Поправка по ходу прогона: после каждой решённой задачи `out_mean` её типа сдвигается к факту
      (среднее с априорным весом `prior_weight` псевдо-наблюдений из конфига) — скрытый набор может отличаться от
      наших шаблонов.
- [x] Двухфазный прогон в `run_agent.py`: фаза A для всех задач без LLM — детектор (`hard` → пропуск) и сборка
      промпта (`Stage1Solver.prepare` → сообщения + `prompt_chars`); фаза B — `TaskPlanner` упорядочивает по
      `reward / mean` и допускает задачу, только если `remaining − reserved ≥ high`; оценка резервируется
      в `BudgetLedger` на время решения и снимается по факту. Задача, не прошедшая допуск, не блокирует более
      дешёвые за ней (`skipped_budget` в журнале).
- [x] В журнал задачи и вызова пишутся `prompt_chars`, `estimate_mean`, `estimate_high` — следующие калибровки
      без пересборки промптов.
- [x] Точность оценки (офлайн, `tools/calibrate_cost.py --eval`): WAPE `mean` по задачам на прогоне, на котором
      **не** калибровали, ниже, чем у старых констант; доля задач с фактом выше `high` ≤ 15 %.
- [ ] Польза выбора (офлайн, `python -m tools.simulate_budget <tasks-dir>=<log> --budgets 0.25 0.5 0.75`):
      проигрыш журнала с фактической ценой задач при бюджете 25/50/75 % от полного расхода; новый планировщик
      набирает баллов не меньше старого на каждом уровне и ни разу не превышает бюджет (старый — считаем, сколько
      раз превысил бы).
- [x] Регрессия: прогон на 8 примерах — 8/8, расход не выше прежнего (± шум модели); тесты зелёные.
- Ключевой критерий парой (тесты в `tests/test_cost_model.py`):
  - должно пройти: бюджет 1000, задачи A (reward 10, high 600) и B (reward 10, high 300), обе в работе
    одновременно — допущены обе только если сумма `high` ≤ 1000; при бюджете 800 допускается одна (B — выше
    `reward/mean`), вторая — `skipped_budget`;
  - должно быть отклонено: задача с `high` больше остатка за вычетом резерва — не стартует, даже если
    `remaining ≥ high` без учёта резерва (сейчас стартовала бы).

## Итог реализации (2026-11-07)
- Отступления от плана: вход — `prompt_chars / chars_per_token[type]` без `overhead_tokens` (общая прямая дала
  сдвиг −175 токенов: search ~2.8 симв/ток, math ~3.9); шаблон повтора хранится в символах (`retry_prompt_chars`).
- Точность (`calibrate_cost --eval`, 120 задач: gen3 × 2 + примеры, половины по task_id): WAPE 0.230 против
  1.013 у констант; факт выше `high` — 8.3 % (coding 9 %, math 10 %).
- Перекалибровка 2026-11-09 (промпты этапа 1 короче — `specs/token-cuts/spec.md`): run29/30/31, 187 задач,
  `--keep-stage2`. Прежние параметры на новых журналах: WAPE 0.60, оценка выше факта на 35 % (search 272 против 88).
  Новые на отложенной половине: WAPE 0.368; факт выше `high` при p90 — 15.5 % (coding 24 % из-за этапа 2, data 17 %
  на 4–7 %), при p95 — 10.2 % (coding 13.7 %, data 15.1 %) и те же баллы в симуляции → выход `high` этапа 1 — p95
  (ключ `out_high`, решение владельца), не ниже `mean` (у search квантиль 13 < среднего 14).
- Симуляция (`simulate_budget`, бюджет 25/50/75/90 %, со вторым проходом по отложенным): баллы
  134/230/277/303 против 112/189/271/299; перерасход 1 из 24 сценариев (бюджет 25 %, факт выше `high`) против 18
  у старого. Критерий «ни разу не превышает» **не выполнен** (отметка снята); p95 вместо p90 даёт 0 перерасходов
  ценой −15 баллов при 50 % — оставлен p90 (`docs/DECISIONS.md`).
- По ревью (`arch-reviewer`): второй проход по задачам, не прошедшим допуск (резервы задач в работе к тому
  времени сменились фактом); сбой детектора — ошибка одной задачи, а не фазы A; масштаб входа — по типу;
  оплаченные вызовы при `budget_exhausted`/`error` — в журнале и в поправке модели; тесты `tests/test_harness_budget.py`.
- Регрессия: примеры 8/8, 20/20, 2191 и 2303 токена (было 1835): в обоих прогонах повтор `search_0001` —
  скрипт модели записал ответ в `answer.txt` и ничего не напечатал («script printed nothing»), вход тот же 2046;
  от модели расхода не зависит. Журналы `logs/run-20261107-123456.jsonl`, `run-20261107-124025.jsonl`.
- Шаг 6 (прогон gen4 вне калибровки) не выполнялся — нужно согласие владельца; вместо него — деление пополам.

## План (шаги)
1. `CostModel` + `config/cost_model.json` (начальные числа — из журналов gen3 вручную) + тесты оценки.
2. `BudgetLedger.reserve/settle`, `TaskPlanner` с допуском по `high` с резервом + тесты пары критериев.
3. `Stage1Solver.prepare/solve(prepared)`, двухфазный `Harness.run`, новые поля журнала; прогон на 8 примерах.
4. `tools/calibrate_cost.py` (калибровка + `--eval`) на парах gen3 + примеры.
5. `tools/simulate_budget.py`; сравнение старого и нового планировщика.
6. Отложенная проверка на данных вне калибровки: прогон ~100 задач из gen4 (≈40–60 тыс. токенов из недельного
   миллиона) — **только с согласия владельца**; без него `--eval` делим gen3 по задачам пополам.
7. `docs/ARCHITECTURE.md` (модуль `cost_model`, поток данных), `docs/DECISIONS.md`, `README`.

## Риски
- Фаза A запускает тесты coding-задач для всех задач до первого вызова LLM: на 100 задачах — минуты; если упрёмся
  в лимит времени (1 ч) — строить промпты потоком впереди решения, а не все сразу.
- Калибровка на своих шаблонах: распределение скрытого набора другое — поэтому поправка по ходу и запас `high`.
